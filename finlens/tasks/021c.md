## Role and context

You are working on **FinLens**, a Flutter personal-finance app. Read
[`CLAUDE.md`](CLAUDE.md) and [`claude/CODEBASE_MAP.md`](claude/CODEBASE_MAP.md) first.

A transfer between two accounts in different currencies is the one entry with **two**
true amounts: what left, and what arrived. Today the form asks for a rate between the
two accounts and computes the arrival from it:

```
   EXCHANGE
   Rate        1 TRY = 0.0227 EUR
   Receives    €22.70                ← read-only
```

Two problems follow from that shape.

**The number the user knows is the one they cannot type.** Nobody reads a rate off
their bank statement; they read *"I sent ₺1,000 and €22.50 landed."* The form asks for
the derived thing and computes the known thing.

**The rate it asks for is not the rate the reports need.** After 021b every entry
carries `rateToBase` against the **reporting** currency. A TRY→EUR rate says nothing
about dollars, so the transfer would need a second rate anyway — and a hand-typed
cross rate that disagrees with the two stored rates makes money appear or vanish on
transfer, a known failure mode in tools that model it this way (Firefly III has an
open issue exactly there).

> **The rules this task implements:** a transfer asks at most **one** rate — the one
> against the reporting currency, the same row every other entry uses. What lands on
> the other side is an **amount**, prefilled from the stored rates and editable,
> because that is the number the user actually has. The transfer's base value always
> comes from the **out** leg: the money left from here, and here is what it was worth.

### 0.1 The exchange group today

```dart

        // not empty.
        if (cross)
          FieldGroup(AppLocalizations.of(context).qaExchange.toUpperCase(), [

                  '${to.currency}',

              opensSheet: true,

            ),
            FieldSpec(
              icon: Icons.check_circle_rounded,
              label: AppLocalizations.of(context).qaReceives,
              value: money(_amount * rate, currency: to.currency),
            ),
          ]),
```

```dart
  double _defaultRate(Account? from, Account? to) {
    if (from == null || to == null) return 1;
    return Fx.rate(from.currency, to.currency);
  }

  Future<void> _editRate(Account from, Account to, double current) async {
    final v = await _promptText(
      title: AppLocalizations.of(context).qaExchangeRate,
      initial: current.toStringAsFixed(4),
      hint: '1 ${from.currency} = ? ${to.currency}',
      numeric: true,
    );
    if (v == null || !mounted) return;
    setState(() => _rateOverride = double.tryParse(v));
  }
```

## 1 · One group, and when it appears

The `EXCHANGE` group's condition widens. It appears when **either**:

- the two accounts' currencies differ (there is an arrival amount to state), **or**
- the *from* account's currency is not the reporting currency (there is a base rate to
  freeze).

It holds, in order:

| Row | When | Value |
|---|---|---|
| the 021b rate row | `from.currency != reportingCurrency` | `1 <reporting> = <rate> <from>` |
| `Receives` | `from.currency != to.currency` | an **amount** in the *to* currency, editable |

**This refines 021b's placement rule, for transfers only.** 021b puts the rate row
last in `REQUIRED`; on a transfer it belongs here instead, beside the arrival it
explains. Keeping currency business in one group is worth one exception — write that
reason into the code, or the next reader will "fix" it back.

Everything else about the rate row is 021b's: the proposal, the `history` / `edit`
markers, the prompt, the 6-decimal entry, the refusal of `0` and negatives, and the
blocker when the currency has no rate at all.

Four shapes result. Verify all four exist after the change:

| from → to, reporting | rows in EXCHANGE |
|---|---|
| TRY → EUR, USD | rate row + `Receives` |
| TRY → USD, USD | rate row + `Receives` |
| USD → TRY, USD | `Receives` only (the out leg is already the reporting currency) |
| TRY → TRY, USD | rate row only (nothing arrives in another currency) |
| USD → USD, USD | the group does not appear at all |

## 2 · `Receives` becomes the number you type

**2a. It is prefilled, not computed-forever.** The first value is derived from the two
stored rates — `amount / rateToBase(from) * rateToBase(to)` — and it keeps tracking
the amount while the user has not touched it. The moment they edit it, it is theirs:
it stops following, and it carries 021b's `edit` marker.

**2b. Editing it sets the cross rate, not the base rate.** `exchangeRate` becomes a
**derived** value — `toAmount / amount` — where it used to be the input. The base rate
the reports use is the rate row's, untouched by anything the user types here. Invert
the doc comments on both fields to say so; their meanings are swapping and a stale
comment here is worse than none.

**2c. It is required when the currencies differ.** `Blocker(unmet: cross &&
toAmount <= 0, label: qaBlockReceives, flashId: 'receives')`. If the destination
currency has no stored rate, nothing can be prefilled — the row starts empty and the
blocker is the only thing standing between the user and a transfer with no arrival.

**2d. The tap target opens an amount prompt**, in the destination currency, using the
same numeric prompt the rate uses. Not the keypad hero — the hero belongs to the
amount that left.

## 3 · What gets stored

```dart
        store.addTxn(
          type: TxnType.transfer,
          amount: _amount,                 // left the from account, in from.currency
          currency: from.currency,
          rateToBase: rateRow,             // 021b: frozen, against the reporting currency
          amountBase: _amount / rateRow,   // the out leg decides the transfer's value
          fromRef: from.id,
          toRef: to.id,
          date: _date,
          exchangeRate: cross ? (toAmount / _amount) : null,   // now derived
          toAmount: cross ? toAmount : null,                   // now entered
          note: _note.text.trim(),
        );
```

## 4 · Editing a saved transfer

- Reopening shows the stored `toAmount` in `Receives` with the `edit` marker if it was
  edited, and the stored `rateToBase` in the rate row under 021b's rules.
- Changing the amount rescales `Receives` **only if the user never edited it**; an
  edited arrival stays put, and `exchangeRate` re-derives.
- Changing either account's currency clears an edited arrival and re-prefills — the
  old number belonged to a different currency.
- `amountBase` always re-derives from `amount` and the frozen `rateToBase`.
