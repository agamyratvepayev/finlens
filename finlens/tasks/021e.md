## Role and context

You are working on **FinLens**, a Flutter personal-finance app. Read
[`CLAUDE.md`](CLAUDE.md) and [`claude/CODEBASE_MAP.md`](claude/CODEBASE_MAP.md) first.

Today the reporting currency is a one-line setting:

```dart
  void setBaseCurrency(String code) {
    if (code.isEmpty || code == _baseCurrency) return;
    _baseCurrency = code;
    notifyListeners();
    unawaited(_saveBaseCurrency(code));
  }
```

That was honest while every figure was converted on read. After 021b it is not: each
entry carries `rateToBase` and `amountBase` **anchored to the reporting currency that
was in force when it was entered**. Flip the setting and every stored base value still
means dollars, while every screen labels it euros. The rates table has the same
problem — it holds "units per one dollar", and nothing says so.

There is no clean fix, because the honest one needs a dated rate for every past day,
and 021a deliberately did not build that. So this task does the next best thing, and
says out loud what it is doing:

> **The rule this task implements:** switching the reporting currency re-expresses the
> whole history through **one** conversion factor, chosen at the moment of the switch.
> March's figure is not "March's real euro value" — it is "March's dollar value, put
> into euros at the rate you switched on". The factor and its date are recorded, so a
> figure that looks odd later can be traced.

Firefly III takes the same path from the other end: it recalculates every stored
amount when the default currency changes, and its docs warn that this can take a long
time and must be re-run if the rates move significantly.

## 0 · The design, verbatim

### 0.1 The setting

```dart
  /// The base currency every total is displayed in — the resolved value, never
  /// null. Reads live so a change in Preferences repaints every aggregate
  /// without an app restart (nothing caches it).
  String get baseCurrency {
    final resolved =
        resolveBaseCurrency(_baseCurrency, _accounts, _deviceLocaleCurrency);
    // Mirror the resolved base into the money formatters so a bare `money(x)`
    // (no currency argument) renders in the base rather than a hard-coded
    // dollar. …
    setFormatterBaseCurrency(resolved);
    return resolved;
  }

  /// The user's explicit choice (More ▸ Preferences). Stores it and notifies so
  /// every total recomputes and repaints immediately.
  void setBaseCurrency(String code) {
    if (code.isEmpty || code == _baseCurrency) return;
    _baseCurrency = code;
    notifyListeners();
    unawaited(_saveBaseCurrency(code));
  }
```

### 0.2 Where it is offered

```dart
/// no-op; a choice repaints every total via [AppStore.setBaseCurrency].
  if (code != null) store.setBaseCurrency(code);
```

### 0.3 What 021b froze onto every entry

```dart
  /// Units of this entry's currency per one unit of the reporting currency, as
  /// it stood when the entry was made … 1 when the entry is already in the
  /// reporting currency.
  double rateToBase;

  /// [amount] in the reporting currency at [rateToBase], rounded once, at entry,
  /// to the reporting currency's decimals.
  double amountBase;
```

### 0.4 The rates table 021a introduced

```dart
  /// How many units of a currency one unit of [baseCurrency] buys …
  /// The base currency is not in the map; its rate is 1 by definition.
  double? rateFor(String code);
  DateTime? rateSetAt(String code);
  void setRate(String code, double rate);
```

## 1 · The factor

Switching from `old` to `new` needs one number: **how many `new` one `old` buys**.
The rates table already holds it — `rateFor(new)` is exactly that, by 021a's
definition. So:

- the switch **proposes** `rateFor(new)` and lets the user edit it, in the same
  numeric prompt 021b uses, refusing `0`, negatives and empty;
- if `new` has no rate, nothing can be proposed: the field starts empty and the
  switch cannot proceed until it is filled;
- the factor is stored with the change record (§5), not recomputed later.

---

## 2 · One transform, applied once

`setBaseCurrency` stops being an assignment and becomes a migration. In one pass,
with `f` the factor:

| What | Transform | Why |
|---|---|---|
| `Txn.amountBase` | `× f`, re-rounded to the new currency's decimals | it was dollars; now it is euros |
| `Txn.rateToBase` | `÷ f` | it meant "per old base"; now "per new base" |
| every entry in the rates table | `÷ f` | same reason |
| the **old** base | **added** to the table as `1 / f` | it is a foreign currency now |
| the **new** base | **removed** from the table | the base is not in the map |
| `Budget.currency`, `Goal.currency` | **untouched** | they are explicit promises, not reporting artefacts |
| `Budget.limit`, `Goal.targetAmount` | **untouched** | ditto — a ₺8,000 budget is still ₺8,000 |
| balances, group totals, net worth | nothing stored to change | they recompute from the new table |

Two invariants must hold afterwards, and both belong in tests:

- for every entry, `amount / rateToBase == amountBase` still holds, to the currency's
  decimals;
- the **ratio** between any two historical figures is unchanged — that is the whole
  claim of a single-factor conversion, and it is what makes the old reports still
  comparable to each other.

State the rounding drift in your report: summing re-rounded values is not the same as
re-rounding the sum, so a month's total may move by cents against `old total × f`.
That is expected; a number that moves by more is a bug.

**Reversibility:** switching back with `1/f` does not restore the original values
exactly, because rounding already happened. Do not try to make it lossless, and do not
hide it — report it.

## 3 · The formatter mirror

`baseCurrency`'s getter mirrors the resolved code into the money formatters, so a bare
`money(x)` follows the base. After §2 that is correct for reporting figures and
**wrong** for every figure that now carries its own currency. Work explore step 3's
list: each entry marked (b) passes its currency explicitly. Do not "fix" this by
changing the mirror — the mirror is right; the call sites are what were ambiguous.

## 4 · What the user is told

**4a. The switch is a confirmation, not a tap.** Choosing a currency in Preferences
opens a sheet before anything changes:

```
   Change reporting currency

   USD  →  EUR

   1 USD =          0.9100 EUR        ⌄

   Past figures are converted with this one rate. They keep
   their proportions but are not re-priced at the rates of
   the time. Budgets and goals keep their own currencies.

   [ Convert and switch ]        Cancel
```

- the rate row behaves as everywhere else: proposed, editable, 6 decimals;
- the button is the only way through; `Cancel` changes nothing at all;
- while `new` has no rate, the button is disabled and the row carries 021a's
  `curSetRate` treatment.

**4b. The Currencies screen records it.** The `REPORTING` row's subtitle gains the
last change: `USD · from TMT on 12 Jun`. One line, the most recent switch only; the
full list lives in the store for anyone reading data, not on screen.

## 5 · The record

```dart
  /// Every reporting-currency switch: what it was, what it became, the single
  /// factor applied to the whole history, and when. Kept because a figure that
  /// looks wrong a year from now is only explicable with this row.
  class BaseCurrencyChange {
    final String from;
    final String to;
    final double factor;
    final DateTime at;
  }
```

Persisted alongside the base currency itself (explore step 7 decides where) and
carried in the backup `meta`.

## 7 · Tests to write

- Unit: after a USD→EUR switch at 0.91, every `amountBase` is the old one × 0.91 and
  every `rateToBase` is the old one ÷ 0.91.
- Unit: `amount / rateToBase == amountBase` holds for every entry afterwards.
- Unit: the ratio between two months' totals is identical before and after.
- Unit: the rates table gains USD at 1/0.91 and loses EUR.
- Unit: budgets and goals keep their currencies, their limits and their targets, and a
  ₺ budget's spend figure is **unchanged** by the switch.
- Unit: balances and net worth are the old ones × 0.91, within rounding.
- Unit: switching with no rate for the target currency is refused.
- Unit: the change record stores from, to, factor and date; a second switch appends.
- Widget: choosing a currency opens the sheet and changes nothing until confirmed;
  `Cancel` leaves every figure identical.
- Widget: the `REPORTING` row shows the last switch afterwards.
- Regression: a single-currency store that never switches is byte-identical.
