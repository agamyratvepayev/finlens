## Role and context

You are working on **FinLens**, a Flutter personal-finance app. Read
[`CLAUDE.md`](CLAUDE.md) and [`claude/CODEBASE_MAP.md`](claude/CODEBASE_MAP.md) first.

`Budget.limit` and `Goal.targetAmount` are bare doubles. Nothing says what currency
they are in, so they are implicitly in the reporting currency — and both are compared
against figures that have been converted into it. That produces two wrong behaviours
that have nothing to do with the user's money:

**A budget widens and narrows on its own.** You live on lira and report in dollars.
Your grocery budget is really "₺8,000 a month", stored as $200. The dollar goes from
40 to 45 lira: the same ₺8,000 is now $178, so the app says you have room you do not
have. The limit never moved; the ruler did.

**A goal walks backwards while you save.** An account-sourced goal measures progress
with `balanceInBase` — the watched account's balance **converted**. A goal on a lira
account with a dollar target slips from 60 % to 54 % overnight because the rate moved,
though the account holds exactly what it held yesterday.

> **The rules this task implements:** a budget is a promise in a currency — usually
> the one you actually spend — so spending in that currency counts **natively, with no
> conversion at all**. A goal that watches an account is measured in that account's
> currency, so the rate cannot move the bar.

### What the user sees

| | Before | After |
|---|---|---|
| New budget | limit, no currency | limit **with a currency**, defaulting to the reporting currency |
| A ₺ budget's spend | every row converted to $ then compared | ₺ rows counted as ₺; other currencies converted |
| Goal on a ₺ account | target in $, progress converted | target in ₺, progress native |
| Goal on a category | target in $ | unchanged — a category spans accounts |

    if (b.scope == BudgetScope.account) {
      return expenseInWindow(window, visible: b.targets);
    }
    return b.targets.fold(
        0.0, (sum, id) => sum + spentInCategoryWindow(id, window));

  /// Rollover carried into the period containing [on] — from the immediately
  /// preceding period only, and only when [repeats] && [rollover] (spec §A.3). A
  /// negative carry (overspending the prior period) is clamped to zero so one
  /// month's overspend never silently shrinks the next.
  double budgetRolloverCarry(Budget b, DateTime on) { … final carry = b.limit - budgetSpendOverWindow(b, prev); … }

  /// The limit that applies in the period containing [on] — base limit plus any
  /// rollover carry (spec §A.3).
  double budgetEffectiveLimit(Budget b, DateTime on) =>
      b.limit + budgetRolloverCarry(b, on);

## 1 · A budget has a currency

**1a. One field, defaulted, chosen at creation.**

```dart
  /// The currency this promise is made in. Spending in it counts as itself —
  /// a ₺8,000 grocery budget must not widen because the dollar moved. Defaults
  /// to the reporting currency, which is what a single-currency user will ever
  /// see.
  String currency;
```

**1b. Spend is measured in the budget's currency.** Replace the two folds so that,
per transaction:

- `t.currency == b.currency` → count **`t.amount`**, untouched. No conversion, no
  rounding, no rate involved. For a single-currency user this is every row, and this
  task becomes invisible to them.
- otherwise → convert `t.amountBase` (frozen, in the reporting currency) into the
  budget's currency **at today's rate**.

The second line is an approximation and you must say so in a comment: a foreign row
inside a lira budget is worth what it was worth in dollars, re-expressed in lira
today. There is no better answer without a dated rate table, which 021a deliberately
did not build. What matters is that the **first** line — the overwhelming majority of
rows — is exact.

**1c. Everything that compares against the limit stays in that currency:**
`budgetSpendOverWindow`, `budgetRolloverCarry`, `budgetEffectiveLimit`, the remaining
figure, the percentage, the warn threshold. The limit is never converted.

**1d. A budget whose currency has no rate** cannot convert its foreign rows, so its
spend figure is null and the card shows 021a's `curRateMissing` in the number's slot,
with 021a's warning card. A budget with **no foreign rows** is fine regardless —
compute first, fail only if a conversion was actually needed.

**1e. Where the currency is chosen and changed.** The new-budget flow and the edit
screen get a currency control beside the limit — the same chip the amount hero uses,
defaulting to the reporting currency. **Changing it does not convert the limit**:
8,000 stays 8,000 and now means 8,000 of the new currency. Confirm that with a
dialog naming both readings before applying, and record it in the budget's history
like any other limit change.

## 2 · A goal is measured where it lives

**2a. One field, derived once, then fixed.**

```dart
  /// The currency [targetAmount] is in. An account-sourced goal inherits the
  /// account's: progress is that account's balance, and measuring it in another
  /// currency makes the bar move when the rate does, not when the user saves.
  /// A category-sourced goal spans accounts, so it uses the reporting currency.
  /// Set at creation and locked with [source].
  final String currency;
```

**2b. Progress stops converting** for account-sourced goals: `start` and `current`
read the account's **native** balance (`balanceOf` / `balanceOn`), not
`balanceInBase` / `balanceOnInBase`. Target, start and current are then all in one
currency and the rate cannot touch the bar.

Category-sourced goals keep `earnedInWindow`, which after 021b sums frozen base
values — reporting currency, matching their target.

**2c. Everything that prints a goal figure** — the editor, the cards, the detail, the
history strings built in the store — passes `g.currency` to `money()`. Explore step 3
is the checklist; a missed one prints lira with a dollar sign.

**2d. The editor's locked chip** now shows the goal's currency and stays locked, for
the reason the source is locked: changing it would silently redefine the target.
