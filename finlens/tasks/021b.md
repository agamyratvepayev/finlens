## Role and context

You are working on **FinLens**, a Flutter personal-finance app. Read
[`CLAUDE.md`](CLAUDE.md) and [`claude/CODEBASE_MAP.md`](claude/CODEBASE_MAP.md) first.

After 021a the rate is a number the user maintains. It is still applied **on read**:

```dart
  double expenseInWindow(DateRange window, {Set<String>? visible}) =>
      txnsInWindow(window)
          .where((t) => t.type == TxnType.expense && …)
          .fold(0.0, (sum, t) => sum + _toBase(t.amount, t.currency));
```

So the moment a user corrects a rate — the whole point of 021a — **March changes.**
A ₺1,250 grocery run entered when the dollar was 38 counted as $32.89; type 40 into
the Currencies screen and the same March expense is now $31.15, the March budget has
room it never had, and last quarter's report has quietly been rewritten. Nothing
about March changed except a number the user entered today.

The fix is the one every serious multi-currency tracker lands on: the rate is part of
the entry, frozen at the moment of entry. Lunch Money stores the rate per
transaction and shows a six-month-old record at that day's rate, not today's.
Firefly III stores the foreign amount alongside the native one and, when rates
change, has to recalculate stored amounts rather than re-deriving them on read.

> **The rule this task implements:** what a foreign entry was worth is decided once,
> when it is entered, and never again. Balances still follow today's rate — those
> answer a different question.

## 1 · Two new fields, filled for every entry

```dart
  /// Units of this entry's currency per one unit of the reporting currency, as
  /// it stood when the entry was made — `1 USD = 40.125 TRY` is stored as
  /// 40.125. Frozen: correcting the currency's rate later never touches it.
  /// 1 when the entry is already in the reporting currency.
  double rateToBase;

  /// [amount] in the reporting currency at [rateToBase], rounded once, at entry,
  /// to the reporting currency's decimals. Every flow figure sums this field, so
  /// a category total and the rows inside it agree to the cent — deriving it per
  /// read would round three ₺100 rows to 2.49 each and their sum to 7.48.
  double amountBase;
```

- Both are **non-nullable**: an entry without a base value cannot be summed, and a
  nullable field would spread `?? ` fallbacks through every report — the same disease
  as `?? 1.0`.
- For an entry in the reporting currency: `rateToBase = 1`, `amountBase = amount`. No
  special case anywhere downstream.
- `addTxn` and `updateTxn` take both. Every caller from explore step 4 supplies them;
  where a caller has no opinion (the seed, the recurrence materialiser), it uses the
  currency's stored rate at that moment and says so in a comment.
- A **rebalance** stores the delta; its `amountBase` is that delta at the frozen rate
  (explore step 5 — confirm before writing).
- Changing `amount` on an edit recomputes `amountBase` **at the stored
  `rateToBase`**, not at today's rate.

## 2 · Flows read the frozen figure

Every sum in explore step 3's flow half stops calling `_toBase` and sums
`t.amountBase`: `incomeInWindow`, `expenseInWindow`, their month twins,
`spentInCategoryWindow`, `earnedInCategoryWindow`, the Insight aggregates, the
same-transactions totals, the scoped-ledger sums, the budget detail.

Rewrite each doc comment: they currently promise conversion ("converted through
`Fx.toBase`"), and that promise is now wrong — they promise a **frozen** figure.

**Undo one thing 021a did.** 021a made flow totals nullable because they converted at
read time and could hit a missing rate. They no longer convert, so they can always be
computed: make them non-nullable again and remove the missing-rate path from the
screens that show only flows. The balance-side totals **stay** nullable — a balance is
still converted today, and today's rate can still be missing. Say in your report
exactly which aggregates changed nullability in each direction.

## 3 · The rate row

A single row, last in the `REQUIRED` group, on every Quick Add form whose current
currency differs from the reporting currency. **Same currency, no row** — a
single-currency user never sees this task.

```
  ⇄   1 USD =                    40.125 TRY   ⌄
```

- label `1 <reporting> =`, value `<rate> <currency>`, rate shown to 4 decimals with
  trailing zeros trimmed;
- tapping it opens the numeric prompt the transfer rate already uses
  (`qaExchangeRate`, `1 X = ? Y`), extended to 6 decimals and refusing `0`,
  negatives and empty;
- it sits inside `REQUIRED` because it is one: without it the entry has no base value.

**3a. What the row proposes.**

| Case | Proposed | Marker |
|---|---|---|
| entry dated today | the currency's stored rate | none |
| back-dated, an earlier entry exists in that currency | that entry's `rateToBase` | `Icons.history_rounded`, 13 pt, `AppColors.textSecondary` |
| the user typed it | what they typed | `Icons.edit_rounded`, 13 pt, `AppColors.accent` |

The marker sits immediately before the value, 5 pt from it. No words: the row is
already three words long, and the marker's meaning is in its semantics label —
`curRateFromEntry` / `curRateManual` — which must be set, because a glyph alone
tells a screen reader nothing.

**3b. The currency has no stored rate at all.** The row renders `curSetRate` in
`AppColors.warning` where the number goes, and a
`Blocker(unmet: …, label: qaBlockRate, flashId: 'rate')` stops the save exactly as a
missing account does. Filling a **blank** rate writes it to the currency's stored rate
as well as freezing it on the entry — the user has just told the app something it did
not know. Overriding a rate that already exists is local to the entry and touches
nothing else. **Report this asymmetry explicitly; it is the one rule here a reader
might not expect.**

**3c. Editing an existing entry** (the rules, in full):

| The user changed | The rate |
|---|---|
| the amount | unchanged; `amountBase` recomputed at it |
| the date | a different rate may now be proposed — ask before replacing, never swap silently |
| the currency | the frozen rate is meaningless; propose the new currency's rate and re-freeze |
| nothing | unchanged |

## 8 · Tests to write

- Unit: an entry in the reporting currency stores `rateToBase == 1` and
  `amountBase == amount`.
- Unit: a ₺1,250 expense at 40.125 stores `amountBase == 31.15`, and **changing the
  currency's stored rate to 45 leaves it at 31.15**.
- Unit: the same change moves `balanceInBase` for that account — balances follow the
  new rate, flows do not.
- Unit: three ₺100 entries sum to exactly the sum of their `amountBase` values, and
  the category total equals the sum of its rows.
- Unit: editing the amount recomputes `amountBase` at the frozen rate.
- Unit: editing the currency re-freezes; editing the date does not, without consent.
- Unit: the proposal picks the nearest earlier entry's rate, and the stored rate when
  there is none.
- Unit: a rebalance's `amountBase` is its delta at the frozen rate.
- Widget: no rate row on a same-currency form; one on a foreign one; Save blocked and
  the row flashed when the currency has no rate.
- Widget: filling a blank rate writes the currency's stored rate; overriding an
  existing one does not.
- Widget: the detail screen shows the base value and the `RATE` row for a foreign
  record and neither for a local one.
- Regression: a freshly seeded store reports the same month totals as before this
